# Changelog

This file tracks real changes to this repository. For the rules on how entries here should be written, see CHANGELOG_TEMPLATE.md.

### Initial interactive purge script and repository setup (round one)

1. Added `scripts/Invoke-EmailPurge.ps1`, an interactive PowerShell 7 script that walks through searching Exchange Online for messages by sender, recipient, subject, and date range, reviewing a preview of the matches, and purging only after a typed `DELETE` confirmation. Sender and recipient are both optional; a subject is required only when neither sender nor recipient is provided, so the search can never be built from nothing. Start and end dates are entered in `yy/mm/dd` format and are optional. The script checks for and creates the `Connect-ExchangeOnline` and `Connect-IPPSSession` sessions automatically if they are not already active, rather than assuming the user has connected beforehand. It offers a choice between `SoftDelete` (recoverable for about 14 days) and `HardDelete` (permanent) at the confirmation step, defaulting to `SoftDelete` if left blank. Every run writes a timestamped transcript under `scripts/logs/` recording the search name, the query used, item counts, and the purge result, so there is an audit trail independent of the Purview portal. This was tested manually against a personal mailbox by searching for a self-sent test message, confirming the abort path leaves the message in place, and confirming the `DELETE` path soft-deletes it.
2. Added the repository's community-health files (`CODE_OF_CONDUCT.md`, `CONTRIBUTING.md`, `SECURITY.md`), issue templates for bug reports and feature requests, and a pull request template, based on the maintainer's standard templates with the project name and repository URL filled in.
3. Added `CHANGELOG_TEMPLATE.md`, the formatting guide for how entries in this file should be written, so future rounds of work follow the same structure.
4. Updated `README.md` with setup requirements, usage instructions for the new script, and a manual testing procedure, replacing the original one-line description.

### Automatic module install (round two)

5. Changed `Ensure-ExchangeOnlineModule` in `scripts/Invoke-EmailPurge.ps1` to install the `ExchangeOnlineManagement` module automatically for the current user when it is missing, and to upgrade it automatically when an installed version is older than the 3.2.0 floor the script's cmdlets require, instead of throwing and telling the user to install it manually. If a version at or above the floor is already present, the script skips installation entirely and just imports it. Updated `README.md` to describe this behavior instead of listing manual installation as a prerequisite.

### Run-from-GitHub documentation (round three)

6. Added a "Run directly from GitHub" section to `README.md` showing the `irm | iex` one-liner for running the script straight from the raw file on GitHub without cloning the repo, and explaining that this path does not trigger PowerShell's execution-policy or unsigned-script checks because those only apply when a `.ps1` file is executed from disk, not when script text is run through `Invoke-Expression`. Noted the one behavioral difference in that mode: since there is no backing script file, the run log is written to `.\logs` under the current working directory instead of next to the script. Documented the `Invoke-WebRequest` plus `Unblock-File` plus `-ExecutionPolicy Bypass` steps as the alternative for anyone who downloads the file and runs it directly instead. Considered adding Authenticode signing to the release workflow so a downloaded copy would not be flagged as unsigned, and decided against it: signing requires an actual code-signing certificate from a CA, a self-signed certificate would not be trusted by Windows without every user manually importing it, and the signature check does not apply to the `irm | iex` path anyway, so it would not have removed the friction it was meant to solve.

### Explicit open-ended date range handling (round four)

7. Made the meaning of a one-sided date range explicit in `scripts/Invoke-EmailPurge.ps1`: giving only an end date omits the `received>=` clause entirely, so the search reaches as far back as indexed mail exists, and giving only a start date omits the `received<=` clause, so the search naturally extends through the moment it runs. This was already the query-building behavior, since a clause is only added when its date was provided, but the script now says so directly. The date prompts were reworded to state this behavior up front, and a "Date range" line summarizing the effective range (both dates, start-only, end-only, or unrestricted) is now printed alongside the query before the search runs, so it shows up in the transcript log as well as on screen.

### Resume unfinished searches and offer cleanup after purge (round five)

8. Added `Get-ResumableEmailPurgeSearches` to `scripts/Invoke-EmailPurge.ps1`, which looks for compliance searches named with this script's `EmailPurge_` prefix that do not have a completed purge action, meaning a previous run was interrupted before purging or before cleaning up. Before asking for search criteria, the script lists any it finds (name, status, item count, and query) and lets the user pick one to resume instead of building a new search, or press Enter to start fresh as before. Resuming skips straight to waiting on the existing search, so an in-progress search is waited on and an already-completed one moves straight to the preview step. Restricting the scan to this script's own naming prefix means it never surfaces or touches another admin's unrelated compliance searches.
9. Added `New-ComplianceActionFresh`, a small helper that removes a leftover preview or purge action under the same identity before creating a new one, since a resumed search or a retried purge can already have a stale or failed action of the same name, and `New-ComplianceSearchAction` fails if one already exists. Both the preview and purge steps now go through this helper.
10. After a purge action reports `Completed`, the script now asks whether to remove the compliance search, defaulting to yes on a blank answer, since the run has already been logged to the transcript at that point and there is nothing left to review. Declining leaves the search in place. If the purge did not complete successfully, the search is always left in place without asking, since removing it would destroy the only path to retrying without starting over; the message tells the user to resume it on the next run. A search with zero matching items is offered the same removal choice immediately, since there is nothing to purge and no reason to keep it around otherwise.

### Broaden resume detection to all compliance searches on request (round six)

11. Changed `Get-ResumableEmailPurgeSearches` in `scripts/Invoke-EmailPurge.ps1` into `Get-ResumableSearches` with an `-AllSearches` switch, so the same unfinished-purge check can run either scoped to this script's own `EmailPurge_` searches or across every compliance search in the tenant. The resume prompt now lists this script's own unfinished searches first, as before, and adds an `other` option: typing it re-runs the check with `-AllSearches`, excludes searches already shown, and lists whatever else turns up so a search someone started manually and never finished can also be resumed and purged through this script. Extracted the search listing and number-to-search-object resolution into `Write-ResumableSearchList` and `Resolve-ResumeChoice` so both the own-searches list and the broadened list use the same selection logic instead of duplicating it.
